# CodeSeek V2: Comprehensive Master System Documentation

---

## 1. Executive Overview & Core Vision

**CodeSeek V2** is an enterprise-grade, repository-grounded artificial intelligence code assistant designed to provide accurate, deterministic, and contextually grounded answers to queries across software codebases. Unlike generic conversational AI systems that rely solely on parameter weights—often resulting in code hallucinations, obsolete references, or inaccurate line mappings—CodeSeek V2 establishes a strict pipeline connecting user queries directly to verifiable source code evidence.

### 1.1 Fundamental Core Principles

1. **Strict Source Grounding**: Every answer, snippet reference, architecture outline, or control flow summary generated by the platform must be directly backed by AST-parsed code chunks stored within the vector repository or retrieved live from source files.
2. **Hybrid Deterministic & LLM Retrieval**: Simple or structural queries (such as file summaries, exact function definitions, directory overviews, or architectural call trees) are fulfilled using high-speed deterministic builders that construct precise answers directly from structural metadata. When a query requires complex reasoning or syntheses across disparate modules, the platform seamlessly routes the context to a Large Language Model with strict evidence constraints.
3. **AST-Driven Semantic Chunking**: Rather than relying on naive text slicing based on fixed character counts or token lengths, CodeSeek V2 uses abstract syntax tree (AST) parsers to chunk source files along functional boundaries (functions, classes, methods, and interface declarations), preserving complete logical scopes.
4. **Multi-Level Hierarchical Knowledge Summarization**: The system automatically computes multi-tiered summaries (chunk-level, file-level, directory-level, and repository-wide) during ingestion. This allows queries targeting macro-level architecture or micro-level implementation details to be answered with equal precision.
5. **Zero Hallucination Circuit Breaking**: Deterministic builders validate the truthiness and non-emptiness of extracted source data before outputting text. If a deterministic path fails to find complete structural evidence, the system triggers an immediate fallback to LLM generation rather than outputting partial or blank responses.

### 2.1 Backend Subsystem

The backend service is powered by Python and FastAPI, serving as the central orchestration controller. It manages:
- Repository cloning, workspace preparation, and index job lifecycles.
- Execution of background worker tasks for asynchronous RAG ingestion.
- Multi-channel API endpoints for session management, conversation history, user authentication, and provider key storage.
- Real-time updates via Server-Sent Events (SSE) to stream indexing logs to the user interface.

### 2.2 Vector Storage Layer (Qdrant)

Qdrant serves as the high-performance vector database, storing high-dimensional vector embeddings of parsed code chunks alongside rich JSON payload metadata. Key features include:
- Payload filtering by repository identifier, session identifier, relative file path, entity type, and language.
- Dense vector similarity search utilizing Cosine metric matching.
- Payload-backed structural exact matching and lexical filter scoring.

### 2.3 Relational Storage Layer (SQLite / PostgreSQL)

Application state management is persisted within a relational database. It maintains:
- User accounts and authentication credentials.
- Repository records, branch state, and commit hash tracking.
- Session metadata and multi-turn conversational chat histories.
- Encrypted AI provider keys (OpenAI, Anthropic, Ollama, local models).
- Structured diagnostic logs and indexing job execution statuses.

## 3. Repository Ingestion Pipeline (Start-to-End)

The RAG (Retrieval-Augmented Generation) Ingestion Engine transforms raw source code files into a structured, vector-indexed semantic database accompanied by a full codebase dependency graph.

```
Raw Git Repository
       |
       v
[ 1. Discovery & Path Enumeration ]
       |
       v
[ 2. Ignore Pattern & Binary Filtering ]
       |
       v
[ 3. AST Parsing (Tree-sitter Engine) ]
       |
       v
[ 4. Structural Semantic Chunking ]
       |
       v
[ 5. Metadata Extraction & Entity Labeling ]
       |
       v
[ 6. Multi-Level Hierarchical Summarization ]
       |
       v
[ 7. Vector Embedding & Qdrant Ingestion ]
       |
       v
[ 8. Dependency Graph Construction ]
```

### 3.1 Stage 1: Discovery & Path Enumeration
- **Input**: Target repository filesystem location or GitHub repository URL.
- **Process**: The discovery stage recursively traverses the repository directory tree, constructing a flattened list of file paths. It tracks directory hierarchies, file sizes, file extensions, and modification timestamps.

### 3.2 Stage 2: Ignore Pattern & Binary Filtering
- **Process**: Filters out unwanted or non-parseable artifacts before processing:
  - Custom user ignore lists and standard version-control ignore configurations.
  - Known binary formats (executables, compiled objects, archives, image assets).
  - Machine-generated build artifacts, lockfiles, and minified bundles.
  - File size safety limits (preventing memory exhaustion from oversized files).

### 3.3 Stage 3: Multi-Language AST Parsing (Tree-sitter Engine)
- **Languages Supported**: Python, JavaScript, TypeScript, JSX, TSX.
- **Process**: Uses Tree-sitter parsers to build exact concrete syntax trees for each source file. Rather than viewing files as arbitrary text strings, the engine extracts syntactical blocks:
  - Class definitions, module exports, and interface specifications.
  - Function declarations, methods, constructors, and arrow functions.
  - Imported symbols, required modules, and package dependencies.
  - Inline comments, docstrings, and type annotations.

### 3.4 Stage 4: Structural Semantic Chunking & Overflow Handling
- **Process**: Splits source code strictly along logical AST boundaries:
  - Small functions and short classes are retained as individual contiguous chunks.
  - Large classes or massive modules are segmented into logical sub-chunks while maintaining parent context headers (class scope declarations, imports, and docstrings).
  - Code overlap parameters ensure that function signatures and decorators remain attached to their respective body code blocks.

- **Oversized Chunk & Overflow Handling Mechanism**:
  When an AST-generated chunk exceeds the maximum permitted token threshold (configured by default to 2,048 tokens), the system passes the chunk to an automated **Overflow Stage** (`handle_overflow`):
  1. **Token Measurement**: Uses token encoding (`tiktoken` with `cl100k_base` encoding) to calculate exact token counts for each semantic block.
  2. **Sliding Line Window Segmentation**: If a chunk exceeds the token cap, the engine divides the content using a sliding line window (default window size of 100 lines).
  3. **Contextual Line Overlap**: Applies a sliding line overlap (default overlap of 20 lines) between consecutive windows. This prevents syntax boundaries, variable declarations, or logical statements from being abruptly truncated across window edges.
  4. **Multi-Part Metadata Tracking**: Each generated sub-chunk inherits all metadata from its parent AST symbol (file path, symbol name, scope depth, import dependencies, and defined symbols) and receives part-tracking attributes (`chunk_part` index and `total_parts` count). Line ranges (`start_line` and `end_line`) are recalculated to reflect absolute file positions.
  5. **Vector Embedding Input Safety Caps**: Prior to embedding generation, code inputs are governed by character-level safety limits (maximum code character caps) to guarantee that vector transformer models operate within safe memory parameters without losing parent symbol context.

### 3.5 Stage 5: Metadata Extraction & Entity Labeling
- **Process**: Enriches each chunk with structured metadata attributes:
  - **Location**: Relative path, starting line number, ending line number.
  - **Scope**: Parent class name, parent function name, scope depth.
  - **Identifiers**: Defined function names, variable names, call expressions.
  - **Entity Type**: Function, Method, Class, Interface, Import Block, File Header, Global Variable.
  - **Metrics**: Cyclomatic complexity estimates, line counts, parameter counts.

### 3.6 Stage 6: Multi-Level Hierarchical Summarization
- **Process**: To support multi-scale queries, the system generates summaries at three distinct structural levels:
  1. **Chunk-Level Summaries**: Concise descriptions of what individual functions or classes accomplish.
  2. **File-Level Summaries**: High-level overviews aggregating chunk descriptions into a coherent breakdown of the file's primary responsibility.
  3. **Repository-Wide Architecture Summary**: A global summary detailing system entry points, database configurations, API routes, and core utility patterns.

### 3.7 Stage 7: Vector Embedding & Qdrant Ingestion
- **Process**: Source code text and metadata summaries are converted into dense vector representations using SentenceTransformer embeddings or external embedding APIs:
  - Normalization of embedding vectors for uniform cosine distance evaluation.
  - Batching of vector payload updates to maximize ingestion throughput.
  - Atomic insertion into Qdrant collections with index isolation based on session IDs and repository targets.

### 3.8 Stage 8: Codebase Knowledge Graph Assembly & Storage
Concurrently with vector ingestion, CodeSeek V2 constructs a relational Knowledge Graph sidecar (`code_graph_nodes`, `code_graph_edges`, `code_graph_builds`) that maps out the structural hierarchy and inter-module dependencies of the repository:

1. **Node Schema & Taxonomy**:
   - `repository`: Root node representing the indexed project workspace.
   - `folder`: Directory nodes organizing the filesystem path hierarchy.
   - `file`: Source file nodes (Python, JavaScript, TypeScript, JSX, TSX).
   - `class`, `function`, `method`, `component`: Structural AST symbol nodes extracted during parsing.
   - `external_package`: Nodes representing third-party dependencies (e.g. `fastapi`, `react`, `qdrant-client`).
   - *Attributes*: Each node records `id`, `session_id`, `node_type`, `name`, `qualified_name`, `relative_path`, `language`, `start_line`, `end_line`, `parent_node_id`, `chunk_id` (linking directly to the Qdrant vector payload), `content_hash`, and `metadata_json`.

2. **Edge Taxonomy & Relationship Links**:
   - `contains`: Represents structural filesystem and AST ownership hierarchy (repository contains folder, folder contains file, class contains method).
   - `defines`: Indicates scope ownership where a file or class defines a symbol (function, method, class, component).
   - `imports`: Resolved dependency link pointing from a source file/symbol to the imported target file or external package node.
   - `unresolved_import`: Records import references where local target resolution was ambiguous, allowing fallback string matching.

3. **Edge Confidence Tiers**:
   - `structural`: Direct containment and AST scope definitions.
   - `exact_local`: Resolved relative imports linking to exact workspace source files.
   - `external_package`: Resolved imports pointing to external libraries.
   - `unresolved_raw`: Unresolved raw import string references.
   - `weak_reference`: Dynamic or fuzzy symbol references.

4. **Two-Phase Build Lifecycle**:
   - **Phase 1 (Structural Hierarchy Build)**: Scans ingestion chunks to create `repository`, `folder`, `file`, and symbol nodes, establishing `contains` and `defines` structural edges. Links each symbol node directly to its Qdrant `chunk_id`.
   - **Phase 2 (Import Resolution & Dependency Linking)**: Resolves relative path imports (`import_resolution.py`), creating `imports` edges for target files or external packages, and `unresolved_import` edges for missing targets.
   - **Incremental Build Support**: Full index executions trigger `rebuild_session_hierarchy_graph`, while incremental updates invoke `replace_paths_hierarchy_graph` to update modified paths and prune deleted files without rebuilding the entire graph.

5. **Operational Retrieval Modes**:
   - **Shadow Mode**: Graph expansion executes in the background alongside standard retrieval to compute diagnostic trace metrics without altering search results.
   - **Graph Assist Mode**: Per-query mode enabled via API flags that uses graph neighborhood traversal to enrich vector search candidates.
   - **Active Mode**: System-wide mode where graph traversal directly injects and reranks 1-to-3 hop neighbor chunks into the candidate pool.

6. **API Endpoints & Frontend Interactive Graph Rendering**:
   - Graph data is exposed via REST API endpoints (`/api/v1/graph/...`), serving node details, edge trees, module clusters, and file dependency structures.
   - The React frontend (`frontend/src/components/graph/`) renders the graph on an interactive D3/SVG canvas, allowing developers to pan, zoom, click nodes to view linked code blocks, and inspect retrieval traversal paths.

## 4. Query Processing & Hybrid Search Strategy

When a user submits a query, CodeSeek V2 processes the request through a multi-stage retrieval pipeline designed to maximize precision while minimizing context noise.

```
User Query
    |
    v
[ Query Intent Classification ]
    |
    v
[ Structural Hint & Symbol Extraction ]
    |
    v
[ Multi-Strategy Hybrid Search ]
  +-- Dense Vector Cosine Similarity
  +-- Exact Structural Identifier Matching
  +-- Lexical Keyword Filtering
    |
    v
[ Symbol & Import Tree Expansion ]
    |
    v
[ Source Truth Verification & Grounding Filter ]
    |
    v
[ Context Window Assembly ]
```

### 4.1 Stage 1: Intent Classification
The query intent classifier analyzes user prompts and categorizes them into distinct operational targets:
- **File Summary Intent**: Requests regarding what a specific file or module does.
- **Code Snippet Intent**: Requests for exact implementations of functions, classes, or methods.
- **Architectural Overview Intent**: High-level questions regarding project organization, component separation, or tech stack details.
- **Data Flow Intent**: Operational questions detailing how data passes through functions, APIs, or pipelines.
- **General Explanation Intent**: Open-ended conceptual questions requiring natural language reasoning.

### 4.2 Stage 2: Structural Hint Extraction
The engine scans the query string for explicit code signals:
- File paths, directory paths, and extension patterns.
- Function names, variable identifiers, class names, and camelCase/snake_case terms.
- Specific line range requests or explicit symbol mentions.

### 4.3 Stage 3: Multi-Mode Hybrid Search Execution & Candidate Layers
Retrieval in CodeSeek V2 operates across up to 12 distinct search modes and candidate channels running in parallel or sequence, combining their outputs to prevent missing relevant code:

1. **Dense Vector Search Mode**: Computes high-dimensional cosine similarity between query embeddings and Qdrant chunk vectors using transformer models (e.g. BAAI/bge-small-en-v1.5).
2. **Lexical BM25 Sparse Search Mode**: Evaluates BM25 keyword scores across indexed file paths, signatures, symbols, metadata labels, and raw source text (with English stopword removal and camelCase/snake_case splitting).
3. **Exact Structural Entity Search Mode**: Executes deterministic Qdrant payload queries for exact match candidates based on AST entity identifiers (exact function names, class definitions, variable names, file paths).
4. **Metadata & Label Filtering Mode**: Filters candidates according to specific structural payload attributes (entity type, language, cyclomatic complexity limits).
5. **Code Topic & Feature Routing Mode**: Evaluates pre-configured topic routes (e.g., authentication handlers, evaluation report APIs, Qdrant upsert logic) to directly fetch known core implementation files and target symbols.
6. **Domain Boost & Repo Profile Discovery Mode**: Leverages structural repository profiles to identify domain-level candidates based on file role classifications, tags, and dependencies.
7. **Feature Recall & Intent Discovery Mode**: Automatically detects feature location intents and injects candidates based on structural feature matches.
8. **Framework-Aware Routing Mode**: Identifies software frameworks (FastAPI, React, Express, etc.) and routes queries targeting specific architectural roles (`backend_entrypoint`, `route_registry`, `middleware`, `controller`, `schema`, `migration`) directly to corresponding framework files.
9. **Dependency Graph & Import Tree Expansion Mode**: Traverses the in-memory knowledge graph to pull imported modules, call dependencies, and parent class declarations.
10. **Previous-Turn Conversation History Injection Mode**: Retains multi-turn conversational context by injecting files and symbols referenced in prior turns for follow-up questions.
11. **Local Content & Source Truth Matching Mode**: Matches raw file content directly from disk to ensure index freshness and prevent stale results.
12. **Component Semantic Targeting Mode**: Targets specific frontend components or backend sub-systems based on semantic component tagging.

### 4.4 Stage 4: Candidate Fusion & Intent-Aware Reranking
- **Reciprocal Rank Fusion (RRF)**: Merges candidates across all search modes using RRF scoring:
  `Fusion Score += 1 / (60 + Candidate Rank)`
- **Base Scoring Composition**:
  Calculates a baseline relevance score combining Dense Vector Score (70%), Exact Entity Match Score (15%), Label Boost (10%), and Path/Symbol Boost (5%).
- **Intent-Aware Score Adjustments**:
  - *Behavior Queries*: Penalizes non-essential support artifacts (generic logging, display helpers, error wrappers) by `-0.75` unless explicitly requested.
  - *Overview & Architecture Queries*: Boosts documentation files, system entrypoints, and configuration modules.
  - *Code Implementation Requests*: Grants a high score boost (`+10.0`) to exact symbol definitions over passive reference calls.
  - *Lexical Synthetic Score*: Lexical-only candidates receive a bounded synthetic vector score to ensure critical keyword matches are preserved even if vector similarity is low.

### 4.5 Stage 5: Symbol & Import Tree Expansion
Once top matching candidate chunks are located, the graph expansion engine enriches the context:
- Identifies imported modules referenced inside retrieved chunks.
- Traverses the knowledge graph (up to 3 levels deep) to fetch defined function definitions and type contracts from separate files.
- Includes callee logic and caller context when data flow analysis is required.

### 4.6 Stage 6: Source Truth Verification & Grounding Filter
- Compares retrieved Qdrant payload snippets against the actual file state on disk to guard against index drift.
- Deduplicates overlapping lines across adjacent chunks.
- Enforces strict context budget limits, partitioning chunks into `shown_sources` (displayed in source cards) and `reasoning_sources` (used for LLM context).

## 5. Answer Generation & Deterministic Builder Mechanics

CodeSeek V2 implements a dynamic dual-path answer generation system. It combines deterministic text builders with an LLM generation path to ensure high-fidelity responses.

```
                          Retrieved Context & Query Intent
                                         |
                                         v
                         +-------------------------------+
                         | Dynamic Query Intent Router   |
                         +-------------------------------+
                                  /             \
                   Deterministic Target         General LLM Target
                                /                 \
                               v                   v
            +-----------------------+     +-----------------------+
            | Deterministic Builder |     |  LLM Generation Path  |
            |     Execution Engine  |     |  (System Persona Prompt)|
            +-----------------------+     +-----------------------+
                        |                             |
                        v                             |
            +-----------------------+                 |
            | Truthiness & Content  |                 |
            |   Validation Check    |                 |
            +-----------------------+                 |
             /                     \                  |
        Valid Data              Empty Result          |
           /                         \                |
          |                           v               |
          |               +-----------------------+   |
          |               | Dynamic Fallback to   |---+
          |               | LLM Generation Path   |
          |               +-----------------------+
          \                           /
           v                         v
       +----------------------------------+
       | Exact Value Grounding & Sanity   |
       |       Validation Layer           |
       +----------------------------------+
                        |
                        v
                 Final Response
```

### 5.1 Deterministic Builder Engine

For structural inquiries, deterministic builders bypass the LLM altogether, eliminating latency and guarantees zero hallucination:

1. **File Summary Builder**: Generates structural overviews of specific files, listing module purpose, key functions, exported interfaces, and file statistics.
2. **Code Snippet Builder**: Assembles requested function or class implementations, incorporating parent class headers, decorator declarations, line numbers, and file locations.
3. **Architecture Builder**: Constructs system topology views based on high-level summaries, entry points, configuration structures, and service boundaries.
4. **Overview Builder**: Produces directory-level or module-level structural breakdowns detailing component interactions.
5. **Flow Builder**: Traces call trees across functions and files to map out execution sequences step by step.

### 5.2 Truthiness Verification & Dynamic Fallback Circuit Breaker

To prevent empty or whitespace-only answers when deterministic lookup returns insufficient evidence:
- The output of every deterministic builder undergoes a strict **truthiness check**.
- If a builder returns `None`, an empty string, or pure whitespace (due to missing AST mappings or unmatched symbols), the circuit breaker immediately intercepts the execution flow.
- The system automatically triggers a **dynamic fallback** to the standard LLM generation path, feeding all retrieved context chunks into the model to construct a coherent, narrative response.

### 5.3 LLM Generation Path

When non-deterministic reasoning is required (or when falling back from a builder):
- **Persona Prompting**: The system adopts a natural, educational persona designed to explain complex software architectures clearly while grounding every statement in retrieved evidence.
- **Provider Support**: Compatible with OpenAI, Anthropic, Ollama, and locally hosted model runtimes.
- **Context Injection**: Formats retrieved code chunks into structured evidence blocks containing file path headings and exact line numbers.

### 5.4 Post-Generation Exact Value Grounding & Validation

Before streaming or outputting the final response:
- **Exact Value Grounding**: Scans generated text to confirm that variable names, numeric constants, function signatures, and file paths match the underlying source context without unauthorized alterations.
- **Answer Validation**: Checks for completeness, evidence link formatting, and compliance with output guidelines.

## 6. Database & State Storage Model

CodeSeek V2 maintains a robust relational data storage model to track system state, user sessions, repository metadata, and credential safety.

### 6.1 Entity Relational Schema Overview

1. **User Accounts Table**: Stores user identifiers, authentication credentials, and user preferences.
2. **Repositories Table**: Records indexed repository URLs, local workspace storage paths, repository default branches, commit hashes, and last-indexed timestamps.
3. **Indexes Table**: Tracks active indexing jobs, target collection names in Qdrant, status states (pending, processing, completed, failed), total chunks created, and error details.
4. **Sessions Table**: Represents chat conversations associated with specific repositories, holding session titles, creation timestamps, and active provider selection configurations.
5. **Messages Table**: Stores individual conversation turns (user prompts and system responses), associated source evidence card references, diagnostic performance metadata, and token usage metrics.
6. **Provider Keys Table**: Manages API key credentials for AI providers (OpenAI, Anthropic, local runtimes) and custom endpoint URLs.
7. **Diagnostic Logs Table**: Logs operational metrics, execution trace IDs, shadow graph performance metrics, and retrieval scores for debugging and quality monitoring.

## 8. Diagnostics, Quality Assurance & Evaluation Framework

CodeSeek V2 embeds diagnostic capabilities throughout its pipeline to maintain operational reliability and answer quality.

### 8.1 Tracing & Diagnostic Logging
- Every query execution generates a unique trace ID that correlates log events across intent classification, hybrid search scoring, graph expansion, builder execution, and LLM generation.
- Search score breakdowns (vector similarity, exact matching score, lexical boost) are captured and returned in response diagnostic metadata.

### 8.2 Shadow vs. Active Dependency Graph Modes
- **Shadow Mode**: Executes graph expansion logic in the background without affecting primary retrieval scoring, recording metrics to compare graph-assisted vs standard vector retrieval precision.
- **Active Mode**: Fully incorporates graph node proximity and import paths into candidate reranking.

### 8.3 Automated Evaluation Suite (.codeseek-evals)
- Benchmark test framework that evaluates model answers against predefined ground-truth Q&A datasets.
- Measures answer correctness, hallucination rate, source line retrieval accuracy, and latency.

### 8.4 Comprehensive Testing Framework
- **Unit & Integration Tests (Pytest)**: Validates AST parsers, semantic chunkers, vector searcher modules, intent routers, and deterministic builders.
- **Frontend Component Tests (Vitest)**: Tests UI component state, source card rendering, and diagnostic modal interactions.
- **End-to-End Tests (Playwright)**: Verifies full browser workflow execution from repository entry and indexing log streaming to chat interaction and response verification.

## 9. Security, Encryption & Multi-Tenant Isolation

Security and data safety are built into every layer of CodeSeek V2.

### 9.1 AES-256 GCM Credential Encryption
- All user-configured API keys (OpenAI, Anthropic, custom tokens) are encrypted before being written to the database using AES-256 GCM authenticated encryption.
- Encryption keys are derived using application master keys configured via environment variables.

### 9.2 Vector Payload Tenant Isolation
- Qdrant vector collections enforce strict payload filtering based on session IDs, user IDs, and repository keys.
- Search queries issued by one session cannot access vector embeddings or metadata chunks belonging to another session or repository context.

### 9.3 Safe Process Execution & Isolation
- Background process execution (git cloning, file enumeration) runs within constrained worker boundaries with strict path traversal checks (`..` prevention) and sandbox restrictions.
- Ingestion parsing enforces safety timeouts and file size limits to mitigate resource exhaustion attacks.
